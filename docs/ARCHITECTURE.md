# Architecture

A static site with a pure calculation core, a registry that drives everything
downstream of it, and a quality gate that decides what is allowed to exist
publicly.

## Shape

```
Rulesets (data)  ──►  Engine (pure)  ──►  Presenters  ──►  Templates
      │                                        ▲
      │                                        │
      └──────────►  Registry  ─────────────────┘
                       │
                       ├─► routes, navigation, breadcrumbs
                       ├─► metadata, structured data, sitemaps
                       ├─► analytics identifiers
                       └─► page manifest ──► indexability gate
```

Data flows one way. Nothing downstream writes back, and nothing upstream knows
about HTML.

## Layers

### `src/data/jurisdictions/` — rules as data

One versioned ruleset per jurisdiction and tax period, holding rates,
thresholds, contributions, and — as first-class fields, not comments — its
provenance: which official source, checked by whom, on what date, expiring when.

Validated by `src/lib/validation/ruleset-schema.ts` at import time. The schema
rejects a published ruleset that has no populated data, no sources, or no
checked-on date, so unsourced figures cannot be published by editing one field.

### `src/lib/calculations/` — the engine

Pure, deterministic, and free of any knowledge of the web. Runs identically at
build time and in the browser.

- `common/money.ts` — decimal money over `big.js`. Never floating point.
- `common/brackets.ts` — progressive bands, tapers, levies. Knows no rates.
- `common/engine.ts` — the shared salary engine every market composes from.
- `common/scenarios.ts` — bonus, pay rise, net-to-gross, each a real comparison.
- `common/net-to-gross.ts` — bounded bisection with round-trip verification.
- `<jurisdiction>/options.ts` — profile handling, no registry dependency.
- `<jurisdiction>/index.ts` — the registry-bound entry point.
- `global/` — mortgage and hourly. No tax data, so live today.

The split between `options.ts` and `index.ts` in each jurisdiction is what keeps
Zod and the ruleset registry out of the browser bundle. See D-008.

### `src/lib/registry/` — the calculator contract

A `CalculatorDefinition` is the single source of truth for a calculator's
routes, fields, validation, metadata, structured data, breadcrumbs, related
links, analytics identifiers, sitemap entries, indexability, and tests.

The 20 per-market tax tools are generated by `factories/salary-tax.ts` from one
jurisdiction description each. That is what stops the site becoming twenty
hand-maintained near-duplicates: a change to how bonus pages present a result is
made once and applies everywhere. They share plumbing, not content — fields,
sources, assumptions, and limitations all come from the jurisdiction's own
ruleset.

Adding an ordinary calculator requires no edit to any route template, sitemap
code, navigation code, analytics code, or structured-data code.

### `src/lib/seo/` — the gate

`manifest.ts` enumerates every page the site can emit and decides, for each,
whether it passes the quality gate and — when it does not — exactly why.

Templates read `indexable` from it. Sitemaps read `inSitemap`. The audit reads
`blockers`. There is one answer, in one place, and the reason travels with it.

### `src/components/` and `src/pages/` — presentation

Astro components with no business logic. `CalculatorPage.astro` and
`SalaryResultPage.astro` are the two page bodies; every calculator route renders
one of them, so form layout, result ordering, ad placement, and source display
are defined once.

## The gate

A page is indexable only when all of the following hold:

- its ruleset is published, populated, dated, sourced, and unexpired;
- the calculator declares assumptions, limitations, fields, and test fixtures;
- a tax tool cites at least one source carrying a checked-on date;
- title, H1, and description are present and unique;
- there is exactly one canonical link and exactly one `<h1>`;
- no placeholder copy appears in the rendered body;
- `SITE_ALLOW_INDEXING` is `true` for this deployment.

A page that fails is emitted with `noindex,follow` and excluded from every
sitemap. `scripts/check-indexability.ts` then re-checks the built HTML and fails
the build if the two ever disagree — so the gate is verified, not trusted.

Indexing is opt-in twice: the page must pass, and the deployment must permit it.
Preview and branch deploys set nothing, so they are noindex by construction.

## Client-side

The page works before its JavaScript loads. The form is a real GET form with a
real submit button, and prefilled salary pages carry their result in the static
HTML.

The client script upgrades submission to in-place recalculation, announces the
result through a live region, and rewrites the query string so the page can be
shared — while the canonical link keeps pointing at the clean tool path, so
query variants never become crawlable URLs.

Measured: 15.3 KB of JavaScript gzipped, 5.2 KB of CSS. Budgets are 60 KB and
30 KB.

## Deliberate absences

No database, no accounts, no sessions, no CMS, no server. No UI framework, no
CSS framework, no charting library — the deduction bar is a flex container with
percentage widths, and every segment is duplicated as a table row.

Calculator inputs never leave the browser. This is enforced by the analytics
adapter, which drops any property outside its allow-list and validates
closed-set values by membership against sets generated from our own registries,
and it is tested by watching the network in `tests/e2e/privacy.spec.ts`.
